CHAPTER 1: AIM AND ABSTRACT

1.1 Aim

To design and develop FLASHDEAL PRO: E-Commerce Flash Sale Simulator in Java using Object Oriented Programming concepts, so that limited promotional inventory can be stored, searched, atomically updated, and processed concurrently under extreme shopping rush without race conditions, overselling, or negative stock.

1.2 Abstract

This project is an advanced e-commerce flash sale simulation desktop application developed in Java Swing. It is used to emulate high-velocity "Big Sale Day" flash events where hundreds of customers compete simultaneously for limited stock items. The program uses classes and objects, encapsulation, inheritance, abstract classes, interfaces, custom checked exceptions (OutOfStockException), multithreading (Thread, Runnable), thread synchronization barriers (CountDownLatch), monitor locking (synchronized), and the Java Collections Framework (LinkedHashMap, ArrayList, Iterator). Transaction records and catalog data are persistently stored using standard RFC-4180 compliant CSV files with atomic stream locks.


CHAPTER 2: INTRODUCTION AND PROBLEM STATEMENT

2.1 Introduction

In modern e-commerce ecosystems during mega-sales events (such as Flipkart Big Billion Days, Amazon Great Indian Festival, or limited-quantity product drops), thousands of shoppers click "Buy Now" at the exact same second. A robust software architecture is critical to guarantee data consistency and fairness under sudden concurrency spikes. Java is particularly well-suited for this domain because it is object-oriented, strictly typed, platform-independent, and provides built-in enterprise-grade concurrency utilities (java.util.concurrent), atomic synchronization primitives, and powerful data structures such as LinkedHashMap and ArrayList.

2.2 Problem Statement

In traditional or uncoordinated systems, when multiple threads access and update shared inventory variables at the same instant, critical section race conditions occur: multiple customer threads read stock = 1 simultaneously and approve purchases, leaving inventory negative (stock = -49), double-selling units to multiple distinct customers, and crashing the user interface.

2.3 Proposed Solution

The proposed Java application addresses these challenges through:

  • Add and store records: Maintain a structured catalog of consumer electronics products in Indian Rupees (₹).
  • Search and update records: Search products dynamically by keyword, filter by category, and adjust inventory levels in real time.
  • Perform atomic purchase operations: Encapsulate check-and-decrement inventory operations within a synchronized critical section.
  • Simulate concurrent shoppers: Launch up to 500 competing customer threads simultaneously using a CountDownLatch(1) release barrier.
  • Display real-time visual reports: Render executive KPI cards, high-contrast live activity logging, and audited transaction ledgers in a responsive Swing GUI.
  • Save data permanently: Store products, customers, and order history using thread-safe CSV file I/O.

CHAPTER 7: PROGRAM LOGIC (ALGORITHM)

7.1 Main Program Flow

  1. Start the program: Main.java executes and configures the modern UI Look-and-Feel.
  2. Load saved data into collection: Load CSV records into memory (products.csv, customers.csv, orders.csv).
  3. Display the main menu: Launch MainFrame with sidebar navigation and show the Executive Dashboard.
  4. Read the user's choice: User selects one of the operational panels (Catalog, Simulator, Order History, Reports).
  5. Configure flash sale simulation: User selects product, configures customer count (1–500), units, and coupon code.
  6. Perform the operation: FlashSaleCoordinator spawns concurrent threads, releases CountDownLatch, and executes atomic purchases.
  7. Validate and handle exceptions: Stock checked inside synchronized (inventoryLock); throws OutOfStockException if exhausted.
  8. Save data to file: Append executed transactions atomically to orders.csv and update product stock in products.csv.
  9. Repeat until user selects Exit / Stop.

7.2 Algorithm for the Core Operation (Atomic Stock Deduction)

  1. Validate inputs: Verify that customer ID, product ID, and requested quantity (> 0) are valid.
  2. Acquire monitor lock: Enter synchronized (inventoryLock) critical section.
  3. Check availability: If currentStock < requestedQuantity, throw OutOfStockException.
  4. Decrement stock atomically: Deduct requested units: remainingStock = currentStock - requestedQuantity and update map.
  5. Exit lock & calculate discount: Evaluate coupon strategy via calculateDiscount(total, qty).
  6. Record transaction: Create Order with status SUCCESS (or OUT_OF_STOCK if exception caught), persist to CSV, and notify UI listeners.

8.2 Key Classes and Code

Class: Inventory | Purpose: Thread-safe monitor ensuring atomic check-and-decrement stock operations

public int deductStock(String productId, int requestedQuantity) throws OutOfStockException {
    if (requestedQuantity <= 0) throw new IllegalArgumentException("Quantity must be positive.");
    synchronized (inventoryLock) {
        int currentStock = stockMap.getOrDefault(productId, 0);
        if (currentStock < requestedQuantity) {
            throw new OutOfStockException(productId, requestedQuantity, currentStock);
        }
        int remainingStock = currentStock - requestedQuantity;
        stockMap.put(productId, remainingStock);
        return remainingStock;
    }
}

Class: FlashSaleCoordinator | Purpose: Multi-threaded start barrier releasing concurrent shoppers simultaneously

CountDownLatch startLatch = new CountDownLatch(1);
CountDownLatch completionLatch = new CountDownLatch(totalCustomers);
for (Customer customer : customers) {
    threadPool.submit(new CustomerPurchaseTask(
        customer, product, unitsPerCust, couponCode, flashSaleService, startLatch, completionLatch
    ));
}
startLatch.countDown(); // Barrier lifted: all customer threads race simultaneously

CHAPTER 11: RESULTS AND DISCUSSION

11.1 Results

The program works correctly for all the operations listed above. Under extreme concurrency stress testing (50 concurrent shopper threads simultaneously competing for 10 physical stock units), the application achieved 100% data consistency: exactly 10 units were sold, exactly 40 out-of-stock attempts were blocked, and available inventory dropped strictly to 0 without ever going negative or double-selling.

11.2 Challenges Faced

Problem Solution in Java
Race conditions in inventory deductionEncapsulated availability check & decrement in synchronized (inventoryLock).
Worker threads freezing Swing GUIDecoupled simulation threads from EDT using SwingUtilities.invokeLater.
Negative payable totals with couponsEnforced .min(totalAmount) in DiscountStrategyBase template method.
CSV data corruption under concurrent writesApplied synchronized file appending in FileStorageService.

11.3 Advantages

  • Guaranteed thread safety and zero overselling under heavy concurrency.
  • Highly extensible architecture using the Strategy Pattern for discounts.
  • Modern, responsive desktop GUI with real-time activity streaming.
  • Pure Java file-based persistence with zero third-party database dependencies.

11.4 Limitations

  • Runs on a single JVM without distributed network sockets or external database clusters.
  • Maximum tested concurrency within default JVM stack memory is 500 simultaneous threads.

11.5 Future Scope

  • Database connectivity using JDBC and SQLite / PostgreSQL.
  • Network socket client-server architecture enabling multiple client laptops.
  • Priority customer queues (e.g., VIP / Prime shoppers).
  • Dynamic real-time charting using JFreeChart.
